## Reference Project Boundary

`gosky` is the committed API/RPC reference project for gofly evolution. New
gofly modules and engineering capabilities should first be aligned with this
project through a repeatable test, smoke report, or generated-output contract.
The project preserves generated source and adds product-specific extensions
under `internal/`.

Repository-level ownership and acceptance expectations are recorded in the
[gosky reference contract](../../docs/reference/gosky-reference-project.md).

## Tenant-Scoped Casbin Authorization

The protected REST example `GET /api/v1/projects/{id}`, unary HTTP-RPC example
`greeter/SayHello`, and opt-in mux stream probe `greeter/Watch` use Casbin only
after a bearer JWT has been verified. Set a distinct, 32-byte-or-longer
development secret before starting the service:

```sh
export GOSKY_JWT_SECRET='replace-this-development-secret-with-at-least-32-bytes'
go run ./cmd/gosky
```

The authenticated JWT must carry `sub` and `tenant_id`. The model and
development-only policy live in `etc/authorization/`; no REST header or RPC
metadata field can override the verified tenant claim. REST resources use their
route template; unary RPC resources use `rpc:<service>/<method>` and the
`CALL` action; mux streams use the same resource format and the `STREAM`
action. The mux probe remains disabled by default and is only registered when
both `rpc.mux.enabled` and `rpc.mux.probe` are enabled. See
[docs/authorization/README.md](docs/authorization/README.md).

## Project Persistence and ABAC

The Project route uses MySQL as its authoritative resource-state store. Its
tenant/owner, active-member, and operation-audit tables are defined in
[`20261001042731_project_authorization.up.sql`](internal/migrations/20261001042731_project_authorization.up.sql)
and its generated
[`20261001042731_project_authorization.down.sql`](internal/migrations/20261001042731_project_authorization.down.sql).
They are a standard `gofly migrate` pair and must be applied using the
deployment-approved runner, then configure a MySQL DSN outside the repository:

```sh
# Run from the gofly repository root until this CLI version is installed.
go run ./cmd/gofly migrate validate --dir examples/gosky/internal/migrations --json
go run ./cmd/gofly migrate up --driver mysql --dir examples/gosky/internal/migrations --dsn-env GOSKY_MYSQL_DSN
```

The `up` command must be executed only by the deployment migration job, never
by the service process. An installed `gofly` binary is equivalent only when
`gofly migrate --help` lists `create|gen|validate|up|down|status`.

```sh
export GOSKY_MYSQL_DSN='gosky:password@tcp(mysql.example:3306)/gosky?parseTime=true&charset=utf8mb4'
```

Set `projectStore.enabled` to `true` only after the migration and DSN are
available. The service never performs schema migration at startup. Project
reads require the verified JWT tenant to match the stored Project tenant and
then allow an owner, active member/collaborator, or tenant-scoped Casbin
`reader`/`writer`/`admin`. Casbin roles are hierarchical: `writer` inherits
`reader`, and `admin` inherits `writer`. A cross-tenant Project returns `403`; an unknown Project
returns `404`. Project and tenant IDs are positive unsigned 64-bit decimal
values. Each decision must be written to `opslogs`; an
audit-write failure returns `503` instead of returning an unaudited result.

See [Project MySQL Persistence](docs/persistence/project-mysql-schema.md) for
the table and authorization contract.

## Mux Subprocess Sink Example

The file `etc/secrets/mux-subprocess-profile.example.json` is documentation-only. It is not a runnable profile and is not loaded by default.

To enable a subprocess mux sink, copy the example to `etc/secrets/mux-subprocess-profile.json`, review the command allowlist, working-directory root, timeout, output limit, and environment whitelist, then explicitly enable the `rpc.mux.log.otelCompatible` sink in the service config.

Do not store raw secrets in runtime snapshots, diff plans, or source-controlled config. Prefer `env://...` or root-scoped `file://...` profile references.

## Mux Operator History Tuning

Operator history persistence is disabled by default. When you enable `rpc.mux.log.otelCompatible.operatorHistory`, keep the store under `fileSecretRoot` and prefer the generated defaults unless you have reviewed disk and audit requirements.

Recommended upper bounds for generated production config are `maxActions <= 1024`, `maxBackups <= 3`, `maxSizeBytes <= 1048576`, and `maxLineBytes <= 65536`. The production check accepts omitted values or values within those bounds and fails fast on larger values. `debugReplayCooldown` must be omitted (default) or between `100ms` and `1m0s`; `auditValidateCooldown` must be omitted (default) or between `100ms` and `1m0s`.

## Mux Operator Admin Endpoints

The RPC admin control plane exposes read-only operator history evidence:

- `GET /rpc/admin/mux/operator-actions/audit-schemas` returns the stable audit detail schemas (for example `gofly.rpc_mux_operator_debug_replay_audit.v1`) so external audit systems can parse operator action details without guessing field names.
- `GET /rpc/admin/mux/operator-actions/history/replay` returns integrity verification for the primary and backup history files plus the debug replay cooldown (`cooldownSeconds`, `cooldownRemainingSeconds`). By default it does not return recorded actions.

Replaying recorded actions requires an explicit, higher-privilege opt-in: add `?debugActions=true` together with a valid `token` matching the configured operator approval token. Debug replay is rate limited by the cooldown and every attempt (approved, denied, or rate-limited) is recorded to operator audit history without the action payload.

## Mux Operator Audit Monitoring

Operator audit records that carry a schema marker are validated on the write path. Any violation increments the low-cardinality counter `gofly_rpc_mux_operator_audit_schema_violation_total{action}`. The generated `deploy/observability/prometheus.yaml` includes a `GoflyMuxOperatorAuditSchemaViolation` alert firing on `sum(rate(gofly_rpc_mux_operator_audit_schema_violation_total[5m])) by (action) > 0`, so schema drift is caught in monitoring rather than only in debug logs.
