## Scope

The first iteration covers REST authorization, unary HTTP-RPC authorization,
and the explicitly enabled experimental mux stream probe through the shared
authorization service. All protected transports resolve through the registry to
a canonical capability with the `EXECUTE` action. The mux adapter carries
request metadata only in its routing frame and restores it into the server
stream context before middleware runs. Because the experimental mux API exposes
a concrete stream type, long-lived gosky stream handlers must use
`ReceiveRegisteredMuxMessage` rather than calling `Receive` directly; this
performs a synchronous policy recheck after each transport receive and before
the business handler observes the message, and creates no background
authorization goroutine.

Project ownership and membership checks use the MySQL-backed Project repository.
Persistent Casbin policies, audited role mutation, and distributed refresh are
implemented through MySQL in this evolution. Project ownership and
membership remain resource-state checks and are not copied into Casbin rules.

The capability registry is a deployment-owned code contract. It maps the
current REST, unary-RPC, and mux-stream transport names to abstract capability
identifiers such as `project.read` and `authorization.role.manage`. Tenants can
receive only fixed `reader`, `writer`, or `admin` role bindings; they cannot
create arbitrary capabilities or replace a transport mapping. The registry
does not decide whether a principal may access a particular Project instance:
that relation decision remains in the Project application service.

## Trust Boundaries

- The bearer token is untrusted until signature and claim validation succeeds.
- `subject` and `tenant_id` come only from verified JWT claims.
- Request headers, query parameters, request bodies, and RPC metadata cannot
  select a tenant or a role.
- Mux routing metadata is untrusted transport input. It may carry a bearer
  token, but the JWT signature and verified claims are the only identity and
  tenant source. The stream handler never receives an authorization failure.
- Casbin policy files are trusted deployment inputs. Their path is fixed by
  application configuration and is never accepted from a request.
- Project tenant, owner, and membership data are trusted only after the MySQL
  repository returns them. The request path identifies a Project but never
  selects its tenant, owner, or authorization basis.

- Project member mutations are request input until their subject and
  `viewer`/`editor` relationship role are validated. Their target cannot be
  the persisted Project owner, whose relation is immutable.
- Project operation logs record verified identity and authorization metadata;
  they do not persist JWTs, HTTP Authorization headers, or response bodies.

The additional direct-only, revocation, Project write/action, migration-idempotence and recovery contracts are recorded in [explicit-admin-permissions.md](explicit-admin-permissions.md).

## Dynamic RBAC (tenant-managed roles, menus, and user administration)

The dynamic RBAC evolution makes roles, the menu catalog, and role-menu grants
tenant-managed database state while keeping the capability vocabulary and its
transport mapping deployment-owned. See [dynamic-rbac.md](dynamic-rbac.md) for
the frozen data model, identifier conventions, and transaction boundaries.

| ID | Condition | Expected outcome | Evidence |
| --- | --- | --- | --- |
| DYNA-001 | A role code is empty, oversized, uses non `^[a-z][a-z0-9_]{1,63}$` characters, duplicates another active role in the same tenant, or equals a reserved code (`reader`, `writer`, `admin`) | `400 invalid_argument`; no role row, Casbin rule, or audit row is written | role-directory service unit and MySQL E2E |
| DYNA-002 | A role is created in tenant A | It is invisible and unusable as a policy subject in tenant B; role codes can repeat across different tenants because uniqueness is `(tenant_id, role_code)` | tenant-isolation MySQL E2E |

| DYNA-004 | A role's capability set is replaced | `role_menus` rows, the canonical `p` rules in `casbin_rules`, and `casbin_policy_events` rows commit in one MySQL transaction; on any statement failure the whole transaction rolls back and no partial grant survives | same-transaction repository fault-injection test |
